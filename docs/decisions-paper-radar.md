# paper-radar 决策记录

> 论文日报机器人：爬取计算机 / 飞行器 / 具身智能前沿论文 → LLM 总结 → QQ 群推送。
> 本文件只记"结论 + 理由"，过程讨论留在对话里。

## 一、已确定

### D1 不 fork 任何现成项目，按 InsightArxiv 的四段骨架重写
- **结论**：自建约 400 行的项目，目录结构照 InsightArxiv（`sources / filters / summarize / sinks`），代码不照抄。
- **理由**：
  - `TideDra/zotero-arxiv-daily`（6.1k★）核心是"按 Zotero 库做向量相似度推荐"，用户 Zotero 为空，冷启动无输出，且 AGPLv3 传染。
  - `Vincentqyw/cv-arxiv-daily`（1.5k★）只有爬虫没有 LLM，"加壳"等于二次开发单文件，会返工。
  - `xmkxabc/InsightArxiv`（17★）是唯一四段全链路的项目，但绑死 Gemini + Scrapy，拆解成本高于重写；抄它的**结构**最划算。
- **调研依据**：GitHub Search API 实测，`paper daily qq bot` 命中 0 个仓库，无现成的"论文日报 + QQ"方案。

### D2 总结模型用云端 API
- **结论**：走云端（阿里云百炼 / DeepSeek 一类 OpenAI 兼容接口），不用本地 Ollama。
- **理由**：本地 `qwen3.5:9b` 在 8G 显存上必须混合推理，每篇 30–60s，100 篇要跑一个多小时；云端单日成本量级为几毛钱，不值得省。

### D3 推送目标为 QQ 群，走已有 NapCat 的 OneBot 11 HTTP 接口
- **结论**：推送层单独成 `sinks/`，主程序不感知 QQ 的存在。
- **理由**：本机已有 NapCatQQ Desktop，`POST /send_group_msg` 即可发群消息；把投递做成"抽屉"，以后加邮件/飞书/微信群只新增一个 sink。
- **已知风险**：QQ 单条消息有长度上限（4000 字符量级），长日报需分段或合并转发。

### D4 采集窗口取"最近 48 小时"而非"昨天"
- **结论**：每次抓取覆盖最近 2–3 天，用 arXiv ID 去重，不按"昨天"取数。
- **理由**：2026-10-24 实测，arXiv API 最新发布日期只到 10-22，10-23（周五）的论文尚未入索引，存在约 1 天延迟。写死"抓昨天"会周期性漏数据。

### D5 信息源策略：arXiv 为唯一主源，顶会/期刊只做"质量标签层"
- **结论**：不做多源聚合抓取。采集只走 arXiv API；顶会与期刊以"标签/白名单"方式合并进论文记录，不单独建抓取管道。
- **理由**：
  - 顶会/期刊是**周期性放榜**（ICRA 每年 5 月、CVPR 每年 6 月），不是每日产出。混入"每日日报"会造成 364 天空白 + 某天数百篇涌入，且无法与当日 arXiv 新论文对齐。
  - 绝大多数顶会论文在录用前后都会挂 arXiv，arXiv 本身就是**全集**；顶会信息的作用是判断"这篇值不值得读"，属于排序信号而非数据源。
- **实测可用性（2026-10-24，直连）**：

| 源 | 状态 | 说明 |
|---|---|---|
| arXiv API (`export.arxiv.org`) | ✅ 200，直连可用 | 主源，无需代理 |
| arXiv `comment` 字段 | ✅ 80 篇中 10 篇(12%) 含录用声明 | 零成本质量标签，如 "Accepted at CoRL 2026" |
| HuggingFace Daily Papers | ✅ 经 `hf-mirror.com` 200 | 直连 huggingface.co 超时；镜像返回 upvotes/githubRepo |
| ACL Anthology | ✅ 200 | NLP 顶会全集，静态页可抓 |
| CVF Open Access | ✅ 200 | CVPR/ICCV/ECCV 全量 PDF |
| Semantic Scholar API | ⚠️ 429 限流 | 需申请免费 key 才稳定；能提供引用数与正式 venue |
| OpenReview API v2 | ❌ 403 人机验证 | ICLR/NeurIPS/ICML 录用状态需浏览器或 token |
| ScienceDirect (CJA) | ❌ 403 | 中国航空学报英文版被 Cloudflare 拦 |
| MDPI Aerospace RSS | ❌ 403 | 航空开放期刊 RSS 被拦 |
| 航空学报（中文） | ❌ 不可达 | 中文核心期刊无开放接口 |

- **飞行器是唯一例外**：arXiv 对该领域覆盖最弱，且上述期刊源全部不可用。现阶段接受"飞行器部分靠 arXiv 三分类近似 + 人工补充"，不为此单独建爬虫。

### D6 详细总结页放 GitHub Pages，QQ 里发"每篇自己的锚点链接"（不发文件）
- **结论**：每天生成一个 `daily-YYYY-MM-DD.html`（**不生成 index.html**），每篇卡片带 `id`；QQ 消息里每篇附 `{public_url}daily-YYYY-MM-DD.html#{paper.id}`。
- **理由**：
  - QQ **不能**渲染 HTML 文件：手机 QQ 收到 `.html` 只提示"用其他应用打开"，等于废掉。原"发 HTML 文件"方案作废。
  - 用户要求"只发纯文字 + 每篇附链接"，而非一个总入口链接。
  - **链接必须带日期**：若指向 `index.html`，次日首页换新一期，昨天消息里的链接会跳到"同一位置但不同论文"，历史消息全部失效。带日期 + 锚点的链接永久有效。
- **实测可达性（2026-10-24 直连）**：`ziwenhahaha.github.io` 返回 200 / 0.68 秒；`pages.github.com` 200 / 0.40 秒；`gitee.io` 超时不可用。故 Pages 方案在当前网络下成立，但仍属"依赖外网可达"的风险项。
- **未采纳的替代方案**：QQ 合并转发（零依赖、手机原生），因用户明确要"链接 + 静态网页"而放弃。
- **连带约束**：必须先 `git push` 并等 Pages 构建（约 60 秒）再发 QQ 消息，否则点开是 404。

### D7 每天推 9 篇（每领域 3 篇），一条消息发完
- **结论**：`domains.*.quota = 3`，日报 9 条，约 2000 字，单条 QQ 消息发完，不分条。
- **演变**：初版 15 篇（5/5/5）→ 用户嫌多改为 3 篇 → 最终定为 **9 篇（3/3/3）**。
- **理由**：15 篇会退化成一屏扫过、实际不读的噪声；每领域 1 篇又太少，且单篇选错代价过高。3 篇是"读得完"与"选错还有回旋"的平衡点。
- **连带影响**：LLM 精选仍是全链路最关键的一步（400 选 9）。约 2000 字仍在 QQ 单条上限内，无需分条。
- **可调**：改 `quota` 一个数字即可放大到 5/15 篇，代码无需改动。

## 三、子系统拆分与处理顺序

整体含 4 个可独立验证的子系统，逐个子项目推进，不一次做全：

1. **采集（本轮处理）**：领域→arXiv 分类映射、采集窗口、去重、配额
2. **筛选与总结**：关键词/向量过滤、LLM 结构化输出、成本与并发控制
3. **投递**：QQ 群消息格式、长度策略、失败重试
4. **调度与运维**：定时触发、日志、无新增日的空态处理
